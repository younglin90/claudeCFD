# Local Electrospray Web GUI

## Build

```bash
cmake -S . -B build
cmake --build build
```

## Start

```bash
python3 apps/electrospray_gui_server.py --host 127.0.0.1 --port 8765
```

Open `http://127.0.0.1:8765`.

## What The GUI Runs

- `electrospray_mesh_validate`: validates either a built-in 3D hex mesh or an OpenFOAM
  ASCII `constant/polyMesh` directory.
- `electrospray_case_runner`: reads `runs/<case>/case.json` and runs either:
  - `validate_mesh`
  - `candido_smoke`
  - OpenFOAM-style case validation through `--case-dir <case>`, reading
    `constant/polyMesh` plus `0/U`, `0/p`, `0/alpha`, `0/phi`, and `0/rhoE`

The `candido_smoke` path runs on either the built-in structured hex box or an external
OpenFOAM `polyMesh`. When `mesh_mode` is `openfoam_polyMesh` and `run_mode` is
`candido_smoke`, the runner reads the polyMesh, normalizes it into the solver's
nondimensional box convention (scale by outer diameter, jet axis centred, and the inlet
plane — detected from the `liquid_inlet` patch, else the minimum y — shifted to y = 0),
then runs the EHD solver on it. Verified for box/cut-cylinder external meshes with bounded
mass and divergence over multiple steps. Boundary conditions are still applied by the
solver's geometric classification (not yet by the named-patch `boundary_conditions` block),
and a fully resolved nozzle-tube domain (with the capillary body below the tip plane)
remains a larger follow-up.

## Adjustable Inputs

The GUI writes every visible input into `runs/<case_name>/case.json`. The C++ case runner
currently consumes these groups for `candido_smoke`:

- built-in mesh: `nx`, `ny`, `nz`, `lx`, `ly`, `lz`, `skew`
- geometry: nozzle diameters, nozzle length, collector distance/diameter/speed, contact angle
- material: density, viscosity, permittivity, conductivity, surface tension
- time/VoF: steps, CFL, pseudo viscosity, compression, sharpening, interface width
- charge/electric model: normalized conductivity, charge limiting/subcycling, ohmic closure,
  electric relaxation time-step limiter, Poisson face/hybrid/bounded-vector/Tomar force toggles
- boundary/initialization: open boundary flux, boundary charge advection, developed inlet,
  moving collector wall, preconditioned paper-current jet, contact-angle curvature

## Boundary Conditions

After `Validate Mesh` or `Upload polyMesh`, the GUI fills the patch table. For each patch you
can set:

- role: inlet, outlet, nozzle, collector, wall, symmetry, electrode
- velocity `U`: type plus `(Ux, Uy, Uz)`
- pressure `p`: type plus scalar value
- volume fraction `alpha`: type plus scalar value
- electric potential `phi`: type plus scalar/voltage value
- charge density `rhoE`: type plus scalar value

`Apply Role Presets` rewrites the patch table from the selected roles. Manual edits after that
are stored as-is in:

```text
runs/<case_name>/case.json
runs/<case_name>/boundary_conditions.json
```

Current limitation: both built-in and external-mesh `candido_smoke` runs still apply the
solver's geometric boundary classification (inlet/collector/atmosphere by position), not the
per-patch `boundary_conditions` block. That block is recorded and validated with the case but
is not yet consumed by the solve. Driving the solver from the named-patch boundary conditions
is the next implementation step for genuinely user-defined inlet/outlet/electrode/wall BCs.

## OpenFOAM Mesh Requirements

The importer reads these polyMesh files:

- `points`
- `faces`
- `owner`
- `neighbour`
- `boundary`

### Loading an externally generated mesh (recommended)

When you generate the mesh yourself with OpenFOAM (e.g. `snappyHexMesh`/`cfMesh` on the
CAD case produced by `apps/generate_nozzle_cad.py`) on the same machine that runs the GUI:

1. Set `mesh mode` to `openfoam_polyMesh`.
2. Type the absolute path into the `OpenFOAM polyMesh path` field. The path may point at
   either the `constant/polyMesh` directory **or** the case directory itself — the loader
   descends into `constant/polyMesh` automatically.
3. Press `Load Mesh View` to preview and `Validate Mesh` to run the quality check. Both the
   preview and the validator accept plain or **gzip-compressed** (`*.gz`) polyMesh files;
   gzip files are decompressed transparently.

Binary-format meshes are not supported. The loader returns an actionable error asking you to
re-export as ASCII — set `writeFormat ascii;` in `system/controlDict` before meshing, or run
`foamFormatConvert -ascii`. (The CAD cases generated by this repo already write ASCII,
uncompressed, so they load and validate without conversion.)

Boundary patch names and face ranges are preserved so the GUI can map patches to roles such
as inlet, outlet, nozzle, collector, wall, symmetry, and electrode.

### Uploading from the browser

If the mesh files are **not** on the machine running the GUI, the `OpenFOAM polyMesh 찾아보기`
control uploads/copies the selected `polyMesh` directory (ASCII, uncompressed) into:

```text
runs/uploads/<case_name>/constant/polyMesh/
```

After upload, the GUI automatically fills `openfoam_polyMesh` with that server-side path and
runs the same mesh validator used by CTest.

## OpenFOAM-Style Initial And Boundary Fields

`OpenFOAM case 찾아보기` uploads the whole case subset needed by this solver:

```text
constant/polyMesh/points
constant/polyMesh/faces
constant/polyMesh/owner
constant/polyMesh/neighbour
constant/polyMesh/boundary
0/U
0/p
0/alpha
0/phi
0/rhoE
```

The field reader supports ASCII `uniform` and `nonuniform List<scalar|vector>`
`internalField` entries and patch-level `type` plus `value uniform ...` entries.
The uploaded case is copied under:

```text
runs/uploads/<case_name>/openfoam_case/
```

The runner writes:

```text
runs/<case_name>/openfoam_case_validation/summary.json
runs/<case_name>/openfoam_case_validation/openfoam_boundary_fields.csv
```

This is intentionally OpenFOAM-like input parsing, not an OpenFOAM dependency. It gives the GUI
a direct way to specify initial conditions and boundary conditions through familiar `0/` files.
After a successful upload, the GUI fills both `openfoam_case_dir` and `openfoam_polyMesh`, and
switches `run_mode` to `validate_openfoam_case`. Pressing `Run Case` then re-runs
`electrospray_case_runner --case-dir <openfoam_case_dir>` from the saved GUI case.

Current limitation: this path validates and records those fields; the production
`candido_smoke` solve still needs a follow-up integration step before it advances arbitrary
external `Mesh3D + OpenFoamCaseFields3D` cases.

## Outputs

Each GUI run writes under:

```text
runs/<case_name>/
```

Typical files:

- `case.json`: exact GUI input used for the run.
- `mesh_validation.csv`: mesh validation summary when mesh validation is requested.
- `summary.json`: case runner summary.
- `history.csv`: Candido smoke time history.
